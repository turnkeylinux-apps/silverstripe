# Silverstripe 19.0 testing

## Scope and source decision

Debian 13 Trixie does not package Silverstripe CMS. The appliance installs the
official Silverstripe installer release 6.2.0 from
`https://github.com/silverstripe/silverstripe-installer.git`. The build pins
annotated tag object `64ee1f94e92fed3dd20c205c70d42d3857628451` and commit
`d37c47c527ebb11c747cb60bde1a2c6c9be0f8c4`. Git verifies both objects after
cloning the immutable official release tag over HTTPS.

Silverstripe CMS 6.2 is a supported stable upstream release. It supports PHP
8.4 and MariaDB, matching Debian Trixie. PHP, Apache, MariaDB, Composer, Git,
and extensions come from signed Debian repositories. Composer resolves and
locks the official `silverstripe/recipe-cms` 6.2 patch channel and verifies
package downloads against authenticated repository metadata.

The supported update workflow is:

```sh
silverstripe-update --check
silverstripe-update --apply
```

The check performs Silverstripe's documented Composer patch update as a dry
run. Apply mode stops Apache, updates the supported Composer dependency set,
runs the database build, restores read-only application ownership, and starts
Apache. Administrators should back up the database and uploaded assets and
review upstream release notes before applying an update.

## Known limitations and deferred issues

- The acceptance fixture uses Silverstripe's authenticated application model
  to create page and asset records after proving the real browser login form.
  It does not automate the CMS JavaScript authoring interface.
- The non-mutating updater check is exercised on every acceptance run. Apply
  mode is retained for an administrator-approved maintenance window because
  an update can change application code and database schema.
- MEDIUM, deferred: `tests/v19.sh` removes its local temporary files but does
  not delete the published acceptance page and asset through Silverstripe. A
  run against persistent state would leave uniquely named content and database
  rows. The v19 harness runs the test in a disposable container, and ordinary
  appliance users do not invoke this acceptance script. Add application-model
  teardown if the test is later supported against persistent appliances.
- Docker runtime validation does not repeat installer, kernel, bootloader, or
  physical hardware checks. Silverstripe adds no appliance-specific behavior
  at those boundaries, so the validated Core 19 baseline supplies inherited
  evidence.
